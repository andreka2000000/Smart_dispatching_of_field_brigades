# Backend МаксТелеком — данные, планирование и события

Реализованы загрузка данных, независимая проверка H1–H10, первоначальный план с PyVRP и резервным Go-алгоритмом, журнал всех шести типов событий, дедупликация, перепланирование, ПГП и предупреждения. Событие, новая версия плана и история предупреждений сохраняются атомарно в PostgreSQL. Рабочие экраны Next.js подключены через UI read API. Следующий этап — независимая приёмка и репетиция демонстрации. Текущая версия API — 0.9.0. Персональные сессии, права и собственность данных реализованы. Администратор объединён с диспетчером; инструкция — [ACCESS_AND_WORKSPACE.md](../docs/ACCESS_AND_WORKSPACE.md).

## Запуск через Docker

Из корня репозитория, при запущенном Docker Desktop:

```powershell
docker compose up -d --build --wait
npm run auth:bootstrap
Invoke-RestMethod http://localhost:8080/api/v1/health

# Откройте /login на frontend и войдите своим аккаунтом.
```

Первый запуск создаёт PostgreSQL, применяет миграцию в транзакции и запускает API. Отдельная команда `docker compose --profile demo run --rm seed` намеренно загружает **демонстрационный набор из примеров контракта**: 1 СЦ, 2 сотрудника, 1 узел, 2 дома, 2 типа работ, матрицу 3×3 и 2 наряда. Это не полный обучающий набор организаторов. В сокращённом примере отсутствует ST-017, поэтому список отсутствующих сотрудников в fixture пуст.

Повторный `seed` намеренно заменяет справочник и день. Обычный запуск и перезапуск контейнеров данные не сбрасывают. База сохраняется в томе `magistral_postgres_data`. Для остановки используйте `docker compose stop`; `docker compose down` также сохраняет том. Не добавляйте `-v`, если данные нужны.

API: `http://127.0.0.1:8080`. PostgreSQL: `127.0.0.1:15432`, база и пользователь `magistral`, локальный пароль по умолчанию `magistral_local`. Порт 15432 выбран, чтобы не конфликтовать с уже работающими БД на компьютере. Переопределения: `API_PORT`, `POSTGRES_PORT`, `POSTGRES_PASSWORD` в окружении или корневом `.env`. Пароль в URL должен быть URL-encoded, если содержит специальные символы. Контейнеры доступны с хоста только через loopback.

Сгенерированный код и копия контракта включаются в backend; Node.js при сборке Docker не нужен. Строковые enum проверяются на границе по схеме, а не приведением Go-типа. `fact` намеренно не включён в DTO Order.

## Правила данных и атомарность

Проверяются обязательные поля (включая false и нули), типы, enum, ограничения схемы, уникальность ID, ссылки сотрудников на СЦ, согласованность повторяющихся домов между узлами, оборудование и вместимость, смены и перерывы, тип узла и технология, ссылки нарядов на тип работ, узел и дом. Контрольный срок берётся из входного deadline; календарь РФ повторно не рассчитывается. Проверяются интервалы, latest_start по нормативу и registered_at ≤ now. Ошибка отклоняет весь запрос.

Матрицы квадратные и направленные; диагональ равна нулю, отрицательные значения запрещены. Матрица покрывает все СЦ и дома. При загрузке до справочника покрытие проверяется при следующем PUT reference. Загруженная матрица сохраняется при замене справочника; несовместимая замена отклоняется с 422. Для замены набора с другими точками сначала загрузите матрицу, покрывающую старые и новые точки, затем новый справочник, затем окончательную матрицу. hourly_factors сохраняются как справочные данные, базовый расчёт Travel их не применяет.

Модельные часы устанавливаются из DayInput.now, затем переходят на timestamp каждого принятого события. Они хранятся в PostgreSQL как timestamptz, возвращаются с +05:00 и точностью до секунды. Равные timestamp допустимы, движение назад запрещено. Время само не идёт: для его изменения нужен TIME_TICK или другое событие. Повторный PUT day — явный сброс, поэтому может задать более ранний now.

Все записи сериализуются PostgreSQL advisory lock и одной транзакцией. Проверка актуальных справочников, удаление старых данных и вставка новых выполняются под одним lock. При сбое SQL выполняется rollback; читатели видят только подтверждённое состояние. Последовательность generation не переиспользуется даже после удаления дня. Идемпотентные миграции версий 1–3 применяются атомарно до старта HTTP, включая обновление существующей БД без удаления данных. Пока допускается один общий сериализованный поток записей; длительный расчёт плана выполняется вне lock.

Ошибки имеют форму `{"error":{"code":"…","message":"…"}}`: 400 — JSON/схема/лимит, 422 — ссылки и смысл, 409 — день до справочника или матрицы, 404 — отсутствующие данные/план, 500 — внутренняя ошибка без SQL в ответе. Неизвестные поля и fact игнорируются и не попадают в хранилище DTO. Frontend читает согласованный снимок через GET /ui/v1/days/{date}/workspace.

## Проверки

Проверка всех тестов с реальным PostgreSQL и `go vet` целиком в Docker (локальный Go не требуется), из корня репозитория:

```powershell
docker compose --profile test run --build --rm tests
```

При установленном Go 1.26+ из backend:

```powershell
go test ./...
go vet ./...
$env:TEST_DATABASE_URL='postgres://magistral:magistral_local@127.0.0.1:15432/magistral?sslmode=disable'
go test -count=1 -v ./...
```

Интеграционный тест создаёт отдельную схему в указанной БД и удаляет только её. Проверяет порядок загрузок, матрицу до справочника, ошибки без изменения состояния, сброс дня, новое поколение, сохранение времени после открытия нового подключения и rollback после искусственного сбоя INSERT. Без TEST_DATABASE_URL этот тест явно пропускается. Модульные тесты проверяют обязательные поля, неизвестные поля, игнорирование fact, секунды и направление матрицы.

## Построение и проверка плана

После запуска Docker и загрузки дня:

```powershell
$body = '{"time_limit_sec":10}'
Invoke-RestMethod -Method Post -Uri http://localhost:8080/api/v1/days/2026-10-26/plan -ContentType 'application/json' -Body $body | ConvertTo-Json -Depth 30
Invoke-RestMethod http://localhost:8080/api/v1/days/2026-10-26/plan | ConvertTo-Json -Depth 30
```

POST допускает пустое тело (лимит 300 секунд) или time_limit_sec от 1 до 300. Каждое построение до первого события возвращает plan_version=1; внутренний plan_revision различает повторные снимки. При изменении исходных данных или конкурентной публикации расчёт отклоняется с 409 PLANNING_INPUT_CHANGED. Повторите POST на свежих данных. После первого принятого события POST блокируется 409 EVENTS_ALREADY_ACCEPTED; дальнейшее изменение плана выполняется через события.

HTTP write timeout — 330 секунд. Расчёт выполняется вне SQL-транзакции на согласованном снимке REPEATABLE READ. Публикация под короткой транзакцией сверяет generation, plan_revision и версии справочника/матрицы, затем атомарно сохраняет снимок и текущую версию. PUT day/reference удаляет старые планы каскадно; замена матрицы инвалидирует планы, так как они рассчитаны для прежней дороги. GET ничего не рассчитывает заново; перезапуск API не теряет план.

Алгоритм — детерминированная эвристика вставки. Наряды сортируются по повторности, latest_start и ширине окна. Перебираются подходящие сотрудники, позиции вставки и позиции перерыва; весь хвост маршрута пересчитывается с возвращением в СЦ. При нехватке оборудования выбирается открытый СЦ с наиболее ранним прибытием к следующему визиту. Дорога берётся из направленной матрицы без hourly_factors. Изменение порядка визитов не использует расстояние по прямой или внешние карты.

У каждого сотрудника на смене есть Route, включая пустой маршрут без визитов. BREAK обязателен для маршрута с визитами; RESTOCK пополняет оборудование до capacity. Пустые списки сериализуются как `[]`. При исчерпании бюджета возвращается лучший уже построенный допустимый план, остальные наряды явно находятся в unassigned. Оставляется запас времени на независимую проверку и commit. Отмена запроса отменяет работу с БД.

NO_QUALIFIED_STAFF и NO_EQUIPMENT используются только при доказуемом отсутствии допуска или достаточной вместимости. Неудача эвристики или исчерпание бюджета дают OTHER с объяснением, а не утверждение о глобальной невозможности. Этот baseline не доказывает оптимальность и не перебирает все комбинации заездов в СЦ. Он также восстанавливает точное расписание предложений PyVRP; выбранный результат и сравнение сохраняются в дополнительном поле Plan.optimization. Отключение PyVRP: `OPTIMIZER_URL=` в `.env`, затем пересоздание API.

Проверки размещены в internal/constraints, алгоритм — internal/planning. Валидатор заново проверяет смену, допуск, перерыв, слот, норматив, дорогу, оборудование, СЦ и полноту учёта, не доверяя travel_sec/totals/equipment_after из ответа. Обработчик событий задаёт Previous, EndOverrides, NewOrderAt и все периоды Unavailable из подтверждённого состояния БД. Проверяются заморозка start < now и невозможность нового прибытия до уведомления плюс дорога; клиент не может произвольно менять историю плана.

Тесты включают контрпримеры H1–H10, RESTOCK, закрытый СЦ, отсутствующих сотрудников, ограничение оборудования, детерминизм, исчерпание бюджета, синтетический сценарий 40 сотрудников/400 нарядов, соответствие ответа OpenAPI, сохранение снимков, SQL rollback и защиту от устаревшей публикации. Синтетический тест не является замером p95 на полном наборе организаторов.

## Журнал событий и перепланирование

На загруженном демодне сначала постройте первоначальный план. Пример события и его повторной отправки:

```powershell
$event = '{"event_id":"demo-tick-001","type":"TIME_TICK","timestamp":"2026-10-26T08:45:00+05:00"}'
Invoke-RestMethod -Method Post -Uri http://localhost:8080/api/v1/days/2026-10-26/events -ContentType 'application/json' -Body $event
Invoke-RestMethod -Method Post -Uri http://localhost:8080/api/v1/days/2026-10-26/events -ContentType 'application/json' -Body $event
Invoke-RestMethod http://localhost:8080/api/v1/days/2026-10-26/plan | ConvertTo-Json -Depth 30
Invoke-RestMethod http://localhost:8080/ui/v1/days/2026-10-26/events | ConvertTo-Json -Depth 30
```

Первый вызов даёт accepted=true, duplicate=false и следующую версию. Повтор даёт duplicate=true, исходные plan_version/as_of/processing_ms и не меняет текущий план. Даже после более новых событий или рестарта проверка event_id идёт раньше проверки возраста timestamp. Идентификатор уникален в пределах поколения дня; повтор с тем же ID и другим валидным телом всё равно считается повтором исходного события. Для нового факта используйте новый ID.

| Тип | Обязательные дополнительные поля | Действие |
|---|---|---|
| NEW_ORDER | order | Проверить ссылки и времена, добавить наряд, попробовать вставку в доступные хвосты |
| ORDER_CANCELLED | order_id, reason | Удалить ещё не начатый визит, записать cancelled; начатый визит сохранить |
| VISIT_DELAYED | staff_id, order_id, expected_end | Изменить конец начатого визита и восстановить допустимость хвоста |
| ORDER_TRANSFERRED | staff_id, order_id, actual_end, transferred_to | Сохранить обслуженный визит, сократить его конец, освободить оставшееся время |
| STAFF_UNAVAILABLE | staff_id, reason; until необязателен | Убрать будущие визиты из периода отсутствия, подобрать замену; после until возобновить из своего СЦ |
| TIME_TICK | нет | Продвинуть модельное время, обновить статусы и попробовать распределить ожидающие наряды |

Для всех типов обязательны event_id, type и timestamp. Enum причин и подразделений — строго из OpenAPI. NEW_ORDER.order.registered_at ≤ timestamp, слот относится к этому дню. У VISIT_DELAYED начало не позже timestamp, expected_end позже прежнего конца и не раньше timestamp. У ORDER_TRANSFERRED actual_end лежит между началом и min(timestamp, прежний конец); повторный перевод этого визита с новым ID отклоняется. until должен быть позже timestamp. Несуществующие ссылки и противоречия дают 422; более ранний timestamp — 409 EVENT_OUT_OF_ORDER. До первоначального плана — 409 PLAN_NOT_BUILT, неизвестный день — 404.

Перепланирование сохраняет выполненный и начатый префикс. Остановка со start == timestamp ещё изменяема, кроме явно указанного визита VISIT_DELAYED/ORDER_TRANSFERRED: его сохраняем по правилу start ≤ timestamp этих событий. Допустимые незатронутые маршруты остаются на месте. Для затронутых пересчитывается хвост с BREAK/RESTOCK/возвращением; не поместившиеся визиты пробуются у других сотрудников. Если допустимой вставки не найдено, наряд явно попадает в unassigned, а не исчезает. У уже завершённого маршрута с замороженным DEPOT_END новые визиты не добавляются. При конечном периоде отсутствия возврат к работе моделируется явной остановкой в своём СЦ с соблюдением дороги и его часов работы; это консервативная эвристика.

Факты исполнения (изменённые окончания, регистрация новых нарядов, периоды недоступности и передачи) сохраняются в days.event_state. Миграция 3 добавляет эту колонку и таблицу events без сброса данных. В одной короткой SQL-транзакции фиксируются новый наряд при необходимости, plan_snapshots, events с исходным результатом, document дня, event_state, model_now, current_version и event_count. Ошибка любого шага откатывает всё. После рестарта читается подтверждённое состояние и журнал; повторно исполнять события для восстановления не требуется. PUT day/reference удаляет журнал, снимки и факты старого поколения каскадно. После событий замена матрицы отклоняется с 422: сначала явно сбросьте затронутые дни или справочник, чтобы не оставить журнал без согласованного плана.

События одного дня сериализуются PostgreSQL session advisory lock даже между разными экземплярами API. SQL-транзакция во время расчёта не удерживается. Ожидающие запросы не занимают соединения пула; сессия держателя закрывается после работы, освобождая lock. Перед commit повторно сверяются generation, plan_revision и версии справочников/матрицы. Параллельный сброс дня даёт 409 PLANNING_INPUT_CHANGED и не позволяет воскресить старые данные. Общий бюджет приложения — 9 секунд, поиск ограничен 8 секундами с резервом на валидацию и commit; ожидание очереди входит в бюджет. EVENT_DEADLINE означает, что запрос не подтвердил новую версию: повторите тот же ID, особенно при потере соединения, чтобы выяснить результат безопасно.

### Противоречивые сценарии контракта

В текущем тексте H3 требует один BREAK для любого маршрута с визитами, а H2 запрещает начало любой остановки во время недоступности. Если сотрудник навсегда выбывает после начатого визита, но до допустимого окна обеда, одновременно выполнить H2, H3 и H10 невозможно. Аналогично задержка, пересекающая уже начатую следующую остановку, не позволяет сохранить замороженную историю. Сервис возвращает 422 EVENT_INFEASIBLE и не меняет данные. Ослаблять ограничения без уточнения организаторов он не будет. Это ограничение нужно согласовать перед полным прогоном кейса; тест закрепляет явное отклонение вместо публикации недопустимого плана.

### Проверки событий

Общая команда Docker-тестов выше запускает и событийные сценарии. Проверяются все шесть типов, дубликат после более нового события и рестарта, равные timestamp, отмена на границе начала, сохранение начатых визитов, перенос затронутого наряда другому сотруднику, неизменность незатронутого маршрута, конечная/бессрочная недоступность, возврат в СЦ, конкурентные повторы и разные события, очередь при пуле из двух соединений, отмена ожидания, SQL-сбои после записи снимка/журнала, retry, сброс поколения и событийный сценарий на 40 сотрудниках/400 нарядах. Проверяются реальный PostgreSQL и независимый валидатор; это ещё не полный нагрузочный прогон p95 организаторов.

## ПГП и предупреждения

ПГП вычисляется до распределения при первоначальном плане и перед перепланированием каждого события. Учитываются только work_type.pgp_relevant=true, один access_node_id, известные на now регистрации и минимум 3 ещё не начатых наряда в интервале не больше 60 минут. Граница 60 минут включена, 60 минут + 1 секунда — нет. Сравниваются моменты времени, а не текстовые смещения ISO 8601. Отменённые, переданные и начатые визиты исключаются из порога; визит с start == timestamp также исключается, если именно его обозначило событие задержки/передачи.

Пересекающиеся окна разбираются детерминированно: уже подтверждённые группы имеют приоритет, затем оставшиеся регистрации обрабатываются от ранних к поздним. Каждая группа сохраняет диапазон регистраций не более 60 минут; один наряд не входит в две группы. Состав не зависит от порядка входного массива. Сохраняются стабильные group_id и первое detected_at, в том числе при добавлении членов и рестарте. Реестр инцидентов хранится в event_state.pgp_history. Новая колонка БД не нужна: JSONB миграции 3 совместим с новой структурой.

Наряды ПГП учитываются в pgp_groups, не дублируются в VISIT или unassigned, и увеличивают summary.pgp_orders. TRANSFER_TO_STATION — решение в плане; внешняя отправка в станционную систему не подключена. При отмене части нарядов подтверждённая группа может остаться парой. При одном оставшемся наряде группа снимается, предупреждение закрывается, оставшийся наряд возвращается в обычное распределение: OpenAPI не разрешает одноэлементную группу. История инцидента и предупреждений сохраняется.

Прогноз LATE_RISK рассчитывается по прежнему маршруту с уже известными задержками и недоступностью, **до** автоматического исправления. Если прогноз начала позже latest_start, сохраняются forecast_start, lateness_min (округление вверх до минуты) и время обнаружения. При бессрочной блокировке или невозможном продолжении текущего маршрута прогноз времени не выдумывается: forecast_start может отсутствовать, а сообщение объясняет необходимость вмешательства. Уже отменённые и сгруппированные визиты не задерживают прогноз оставшихся работ.

Если допустимое перепланирование передало наряд другому сотруднику, предупреждение сразу имеет REASSIGN, suggested_staff_id, applied=true, RESOLVED и resolved_at=now, сохраняя исходный прогноз. Если риск снят изменением порядка на том же маршруте — suggested_action=NONE и applied=true. Если допустимой вставки нет, предупреждение остаётся ACTIVE и предлагает RESCHEDULE. proposed_slot — только вариант для согласования, без обещания полной допустимости; исходные slot/latest_start/deadline никогда не изменяются автоматически. При недоступности до конца смены конкретный новый слот не выдумывается.

created_at всегда равно реальному модельному now первого обнаружения эпизода. Требование предупреждать за 30 минут проверяется честно: если причина стала известна позже, сервис не датирует предупреждение задним числом. Активный эпизод сохраняет первый прогноз и время создания; закрытый эпизод неизменяем. Если проблема возникает повторно, создаётся новое alert_id. PGP_DETECTED активно, пока существует группа, с applied=true для группировки в плане. UNASSIGNED активно, пока наряд не назначен, не сгруппирован или не отменён. История alerts только дополняется; все состояния остаются в снимках плана. EventResult.new_alerts содержит только действительно новые ID, включая предупреждения, которые были устранены в том же событии. Повтор события возвращает его исходные предупреждения.

Причины unassigned уточняются только при доказуемых условиях: NO_QUALIFIED_STAFF, NO_EQUIPMENT, STAFF_UNAVAILABLE, NO_SHIFT_TIME, SLOT_UNREACHABLE. Например, истёкший latest_start доказывает невозможность нового визита, а нехватка оставшихся минут даже без дороги доказывает NO_SHIFT_TIME. Неудача ограниченной эвристики по-прежнему даёт OTHER: она не доказывает глобальную невозможность.

Прочитать результаты на текущем дне можно без сброса:

```powershell
$plan = Invoke-RestMethod http://localhost:8080/api/v1/days/2026-10-26/plan
$plan.pgp_groups | ConvertTo-Json -Depth 20
$plan.alerts | ConvertTo-Json -Depth 20
$plan.unassigned | ConvertTo-Json -Depth 20
```

Отдельная демонстрация ПГП ниже **сбрасывает план и журнал дня 2026-10-26** и загружает 3 синтетических обращения с одного узла. Сначала должны быть загружены стандартные reference.json и matrix.json:

```powershell
Invoke-RestMethod -Method Put -Uri http://localhost:8080/api/v1/days/2026-10-26 -ContentType 'application/json' -InFile .\backend\testdata\day_pgp.json
$plan = Invoke-RestMethod -Method Post -Uri http://localhost:8080/api/v1/days/2026-10-26/plan -ContentType 'application/json' -Body '{"time_limit_sec":10}'
$plan.pgp_groups | ConvertTo-Json -Depth 20
$plan.alerts | ConvertTo-Json -Depth 20
```

Ожидается одна группа из 3 нарядов, один PGP_DETECTED и summary.pgp_orders=3. Это демонстрационный набор, не данные организаторов. Тесты дополнительно проверяют пороги 2/3 и 60 минут, разные узлы, исключения, рост/сокращение группы, ранний прогноз до успешного переназначения, возврат исходных предупреждений при дубликате, откат при ошибке SQL и неизменность закрытых записей после рестарта.

## Согласованный снимок для интерфейса

GET /ui/v1/days/{date}/workspace читает день, актуальный справочник, текущий снимок плана и журнал текущего поколения в одной read-only транзакции REPEATABLE READ. Счётчик событий, версия и часы не расходятся при конкурентной публикации. Отсутствующий день даёт 404 DAY_NOT_FOUND; день до расчёта возвращает plan=null. Оба состояния и снимок после события проверяются интеграционным тестом. Docker Compose также запускает Next.js на порту FRONTEND_PORT (по умолчанию 3000).

## Полный учебный набор и дорожная маршрутизация

В data/synthetic находятся файлы организаторских форматов с 40 сотрудниками (28 ЛТП + 12 инсталляторов), 5 СЦ, 400 нарядами и направленной матрицей OSRM. Это собственные синтетические данные, а не официальный набор. npm run demo:load сначала проверяет весь набор, затем создаёт отдельную БД magistral_training, переключает API и загружает файлы. Повторная замена требует --replace. Исходная БД magistral сохраняется. Для возврата измените API_DATABASE=magistral в локальном .env и пересоздайте api. Форматы, дорожный граф и точный запуск — в docs/ROUTING.md и docs/CASE_REQUIREMENTS.md. Сборка backend из корня требует включить каталог data наряду с backend.

OSRM — отдельный необязательный для оценочного API сервис профиля routing. Его недоступность не мешает проверке готовности API, загрузке данных и планированию по матрице; карта получает 503 ROUTING_UNAVAILABLE. Геометрия не меняет порядок визитов, версию плана, модельное время и журнал. Параметры generation/version защищают UI от смешения версий.
