# Backend Магистраль — загрузка данных и базовое планирование

Реализованы загрузка данных, независимая проверка H1–H10 и первоначальный допустимый план по OpenAPI 1.0.0. Планы сохраняются в PostgreSQL. Обработка событий и перепланирование, ПГП, предупреждения и AI остаются следующими этапами.

## Запуск через Docker

Из корня репозитория, при запущенном Docker Desktop:

```powershell
docker compose up -d --build --wait
docker compose --profile demo run --rm seed
Invoke-RestMethod http://localhost:8080/api/v1/health
Invoke-RestMethod http://localhost:8080/ui/v1/days/2026-10-26
```

Первый запуск создаёт PostgreSQL, применяет миграцию в транзакции и запускает API. Второй вызов загружает **демонстрационный набор из примеров контракта**: 1 СЦ, 2 сотрудника, 1 узел, 2 дома, 2 типа работ, матрицу 3×3 и 2 наряда. Это не полный обучающий набор организаторов. В сокращённом примере отсутствует ST-017, поэтому список отсутствующих сотрудников в fixture пуст.

Повторный `seed` намеренно заменяет справочник и день. Обычный запуск и перезапуск контейнеров данные не сбрасывают. База сохраняется в томе `magistral_postgres_data`. Для остановки используйте `docker compose stop`; `docker compose down` также сохраняет том. Не добавляйте `-v`, если данные нужны.

API: `http://127.0.0.1:8080`. PostgreSQL: `127.0.0.1:15432`, база и пользователь `magistral`, локальный пароль по умолчанию `magistral_local`. Порт 15432 выбран, чтобы не конфликтовать с уже работающими БД на компьютере. Переопределения: `API_PORT`, `POSTGRES_PORT`, `POSTGRES_PASSWORD` в окружении или корневом `.env`. Пароль в URL должен быть URL-encoded, если содержит специальные символы. Контейнеры доступны с хоста только через loopback.

## Структура и границы

```text
cmd/server/             запуск, сигналы, таймауты HTTP
cmd/seed/               явная загрузка примеров через API
internal/dto/           Go DTO всех схем OpenAPI, включая Plan и Event
internal/contract/      встроенный контракт и проверка схемы JSON
internal/transport/     HTTP, формат ошибок, лимит 100 МиБ
internal/application/   загрузка, проверки смысла и связей
internal/domain/        модельные часы, плотная матрица с индексом
internal/constraints/   независимая проверка допустимости H1–H10
internal/planning/      базовая эвристика вставки и симуляция маршрута
internal/storage/postgres/ SQL, миграция, транзакции
testdata/               согласованный минимальный набор JSON
tools/generate.cjs      генерация DTO и примеров из исходного контракта
```

Домен не импортирует HTTP, PostgreSQL или решатель. В приложении нет зависимости от Next.js. Секреты задаются окружением; Go не требует авторизации на путях организаторов.

DTO генерируются из неизменённого `contracts/api_spec.yaml`. Для обновления из корня репозитория: `npm ci`, `node backend/tools/generate.cjs`, затем `gofmt -w backend/internal/dto/types.gen.go`. Сгенерированный код и копия контракта включаются в backend; Node.js при сборке Docker не нужен. Строковые enum проверяются на границе по схеме, а не приведением Go-типа. `fact` намеренно не включён в DTO Order.

## API

| Метод | Путь | Результат |
|---|---|---|
| GET | `/api/v1/health` | 200 только после миграции и успешной проверки БД |
| PUT | `/api/v1/reference` | Атомарная замена всех справочников, удаление дней и нарядов |
| PUT | `/api/v1/reference/travel-matrix` | Загрузка/замена матрицы до или после справочников |
| PUT | `/api/v1/days/{date}` | Загрузка/замена нарядов дня, новое поколение, установка now |
| POST | `/api/v1/days/{date}/plan` | Построить и сохранить первоначальный план, версия 1 |
| GET | `/api/v1/days/{date}/plan` | Получить сохранённый план, 404 до первого построения |
| GET | `/ui/v1/reference` | Дополнительное чтение справочника для проверки и будущего UI |
| GET | `/ui/v1/days/{date}` | Данные дня, generation и сохранённое модельное as_of |

Загрузка собственных подготовленных JSON из PowerShell:

```powershell
Invoke-RestMethod -Method Put -Uri http://localhost:8080/api/v1/reference -ContentType 'application/json' -InFile .\backend\testdata\reference.json
Invoke-RestMethod -Method Put -Uri http://localhost:8080/api/v1/reference/travel-matrix -ContentType 'application/json' -InFile .\backend\testdata\matrix.json
Invoke-RestMethod -Method Put -Uri http://localhost:8080/api/v1/days/2026-10-26 -ContentType 'application/json' -InFile .\backend\testdata\day.json
```

Для файлов организаторов массивы `service_centers.json`, `staff.json`, `access_nodes.json` и строки `work_types.csv` необходимо собрать в объект ReferenceData; наряды фильтруются по дате slot.start и registered_at ≤ now. API принимает готовые тела ReferenceData, TravelMatrix и DayInput, а не multipart или пути к файлам. Поля и единицы берутся из контракта: минуты нормативов, секунды дороги, метры расстояний. Production-набор следует загружать после демонстрации.

## Правила данных и атомарность

Проверяются обязательные поля (включая false и нули), типы, enum, ограничения схемы, уникальность ID, ссылки сотрудников на СЦ, согласованность повторяющихся домов между узлами, оборудование и вместимость, смены и перерывы, тип узла и технология, ссылки нарядов на тип работ, узел и дом. Контрольный срок берётся из входного deadline; календарь РФ повторно не рассчитывается. Проверяются интервалы, latest_start по нормативу и registered_at ≤ now. Ошибка отклоняет весь запрос.

Матрицы квадратные и направленные; диагональ равна нулю, отрицательные значения запрещены. Матрица покрывает все СЦ и дома. При загрузке до справочника покрытие проверяется при следующем PUT reference. Загруженная матрица сохраняется при замене справочника; несовместимая замена отклоняется с 422. Для замены набора с другими точками сначала загрузите матрицу, покрывающую старые и новые точки, затем новый справочник, затем окончательную матрицу. hourly_factors сохраняются как справочные данные, базовый расчёт Travel их не применяет.

Модельные часы устанавливаются только из DayInput.now. Они хранятся в PostgreSQL как timestamptz, возвращаются с +05:00 и точностью до секунды. Переход ModelClock.Advance допускает равные timestamp и запрещает движение назад. HTTP событий появится на следующем этапе; сейчас время само не идёт. Повторный PUT day — явный сброс, поэтому может задать более ранний now.

Все записи сериализуются PostgreSQL advisory lock и одной транзакцией. Проверка актуальных справочников, удаление старых данных и вставка новых выполняются под одним lock. При сбое SQL выполняется rollback; читатели видят только подтверждённое состояние. Последовательность generation не переиспользуется даже после удаления дня. Идемпотентные миграции версий 1–2 применяются атомарно до старта HTTP, включая обновление существующей БД без удаления данных. Пока допускается один общий сериализованный поток записей; длительный расчёт плана выполняется вне lock.

Ошибки имеют форму `{"error":{"code":"…","message":"…"}}`: 400 — JSON/схема/лимит, 422 — ссылки и смысл, 409 — день до справочника или матрицы, 404 — отсутствующие данные/план, 500 — внутренняя ошибка без SQL в ответе. Неизвестные поля и fact игнорируются и не попадают в хранилище DTO. Новые backend-эндпоинты ещё не подключены к frontend.

## Проверки

Проверка всех тестов с реальным PostgreSQL и `go vet` целиком в Docker (локальный Go не требуется), из корня репозитория:

```powershell
docker compose --profile test run --build --rm tests
```

При установленном Go 1.26+ из backend:

```powershell
go test ./...
go vet ./...
$env:TEST_DATABASE_URL='postgres://magistral:magistral_local@127.0.0.1:15432/magistral?sslmode=disable'
go test -count=1 -v ./...
```

Интеграционный тест создаёт отдельную схему в указанной БД и удаляет только её. Проверяет порядок загрузок, матрицу до справочника, ошибки без изменения состояния, сброс дня, новое поколение, сохранение времени после открытия нового подключения и rollback после искусственного сбоя INSERT. Без TEST_DATABASE_URL этот тест явно пропускается. Модульные тесты проверяют обязательные поля, неизвестные поля, игнорирование fact, секунды и направление матрицы.

## Последовательность следующих работ

1. Выполнено: независимый валидатор H1–H10, допустимый базовый план, POST/GET plan, снимки версий.
2. Журнал событий, дедупликация, атомарная публикация плана и защита generation.
3. Все шесть событий и локальное перепланирование с заморозкой начатых остановок.
4. ПГП, LATE_RISK, история предупреждений и причины unassigned.
5. UI read API и подключение Next.js к реальным данным.
6. Улучшение оптимизации, проверяемый адаптер PyVRP и необязательный AI-помощник.

Первые пять пунктов требуются для полноценного решения кейса. Наличие базового плана ещё не означает готовность к полному событийному сценарию оценки организаторов.

## Построение и проверка плана

После запуска Docker и загрузки дня:

```powershell
$body = '{"time_limit_sec":10}'
Invoke-RestMethod -Method Post -Uri http://localhost:8080/api/v1/days/2026-10-26/plan -ContentType 'application/json' -Body $body | ConvertTo-Json -Depth 30
Invoke-RestMethod http://localhost:8080/api/v1/days/2026-10-26/plan | ConvertTo-Json -Depth 30
```

POST допускает пустое тело (лимит 300 секунд) или time_limit_sec от 1 до 300. Каждое построение до первого события возвращает plan_version=1; внутренний plan_revision различает повторные снимки. При изменении исходных данных или конкурентной публикации расчёт отклоняется с 409 PLANNING_INPUT_CHANGED. Повторите POST на свежих данных. После первого принятого события POST блокируется 409; сам приём событий ещё не реализован, предусмотрен защитный event_count.

HTTP write timeout — 330 секунд. Расчёт выполняется вне SQL-транзакции на согласованном снимке REPEATABLE READ. Публикация под короткой транзакцией сверяет generation, plan_revision и версии справочника/матрицы, затем атомарно сохраняет снимок и текущую версию. PUT day/reference удаляет старые планы каскадно; замена матрицы инвалидирует планы, так как они рассчитаны для прежней дороги. GET ничего не рассчитывает заново; перезапуск API не теряет план.

Алгоритм — детерминированная эвристика вставки. Наряды сортируются по повторности, latest_start и ширине окна. Перебираются подходящие сотрудники, позиции вставки и позиции перерыва; весь хвост маршрута пересчитывается с возвращением в СЦ. При нехватке оборудования выбирается открытый СЦ с наиболее ранним прибытием к следующему визиту. Дорога берётся из направленной матрицы без hourly_factors. Изменение порядка визитов не использует расстояние по прямой или внешние карты.

У каждого сотрудника на смене есть Route, включая пустой маршрут без визитов. BREAK обязателен для маршрута с визитами; RESTOCK пополняет оборудование до capacity. Пустые списки сериализуются как `[]`. При исчерпании бюджета возвращается лучший уже построенный допустимый план, остальные наряды явно находятся в unassigned. Оставляется запас времени на независимую проверку и commit. Отмена запроса отменяет работу с БД.

NO_QUALIFIED_STAFF и NO_EQUIPMENT используются только при доказуемом отсутствии допуска или достаточной вместимости. Неудача эвристики или исчерпание бюджета дают OTHER с объяснением, а не утверждение о глобальной невозможности. Этот baseline не доказывает оптимальность и не перебирает все комбинации заездов в СЦ. PyVRP пока не подключён.

Проверки размещены в internal/constraints, алгоритм — internal/planning. Валидатор заново проверяет смену, допуск, перерыв, слот, норматив, дорогу, оборудование, СЦ и полноту учёта, не доверяя travel_sec/totals/equipment_after из ответа. Для H10 предусмотрены Previous, EndOverrides и NewOrderAt: проверяется заморозка start < now и невозможность нового прибытия до уведомления плюс дорога. Эти факты позже должен задавать обработчик событий, а не клиент плана. Пока эндпоинта событий нет, H10 действует для первоначального now и проверяется модульными контрпримерами.

Тесты включают контрпримеры H1–H10, RESTOCK, закрытый СЦ, отсутствующих сотрудников, ограничение оборудования, детерминизм, исчерпание бюджета, синтетический сценарий 40 сотрудников/400 нарядов, соответствие ответа OpenAPI, сохранение снимков, SQL rollback и защиту от устаревшей публикации. Синтетический тест не является замером p95 на полном наборе организаторов.
