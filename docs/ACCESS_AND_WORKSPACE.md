# Доступ и архитектура рабочих страниц МаксТелеком

Бренд: **«МаксТелеком — порядок там, где раньше был хаос»**. Изменения относятся к рабочим экранам; композиция главной сохранена, обновлены название и слоган. Реализовано 14 ноября 2026 года, API 0.9.0.

## Три роли

Отдельной роли администратора больше нет. Полномочия администратора включены в DISPATCHER.

| Возможность                                                               | Диспетчер / управление | Исполнитель                              | Абонент     |
| ------------------------------------------------------------------------- | ---------------------- | ---------------------------------------- | ----------- |
| Все наряды, сотрудники, карта смены, ПГП, журнал                          | Да                     | Только свои назначенные наряды и маршрут | Нет         |
| Первоначальный расчёт и все шесть событий                                 | Да                     | Нет                                      | Нет         |
| Сообщить о задержке, передаче своего визита или собственной недоступности | Да                     | Да, сервер проверяет принадлежность      | Нет         |
| Дорожная геометрия                                                        | Любой сотрудник        | Только связанный staff_id                | Нет         |
| Создать обращение на услугу                                               | Принимает обращения    | Нет                                      | Да          |
| Просмотр обращений абонентов                                              | Все                    | Нет                                      | Только свои |
| Ответить и обработать обращение                                           | Да                     | Нет                                      | Нет         |
| Создать и отключить аккаунты                                              | Да                     | Нет                                      | Нет         |
| Справочники и платформа                                                   | Да                     | Только данные для своего маршрута        | Нет         |

Роль и staff_id берутся из аккаунта в PostgreSQL. Параметры URL, заголовки роли, скрытые пункты меню и localStorage прав не предоставляют. Полный снимок диспетчера не передаётся исполнителю с последующим скрытием на клиенте: Go формирует отдельную проекцию.

## Как устроен вход

1. `/login` отправляет логин и пароль через Next.js proxy в Go.
2. Go проверяет пароль, создаёт случайный идентификатор сессии, хранит его SHA-256 в БД и устанавливает cookie `mt_session` с HttpOnly и SameSite=Strict. Срок — восемь часов реального времени, независимо от модельного времени кейса.
3. Next.js проверяет сессию на сервере при открытии защищённых страниц. Пользователь попадает на домашнюю страницу своей роли.
4. Go повторно проверяет сессию, актуальную роль, блокировку и принадлежность данных при каждом запросе API.
5. Выход отзывает сессию в БД и удаляет cookie. Отключение пользователя отзывает все его сессии. Нельзя отключить себя. Для одного сотрудника допускается один активный аккаунт исполнителя.
6. Вкладки сообщают друг другу о смене аккаунта; query cache очищается при выходе. Сессия дополнительно проверяется при возвращении к вкладке и раз в минуту.

Пароли: индивидуальная соль, PBKDF2-HMAC-SHA256, 600000 итераций, сравнение в постоянное время. Приняты меры против перебора логина и запросов изменения состояния с посторонних Origin. Токены не хранятся в localStorage. Для локального HTTP `COOKIE_SECURE=false`; при HTTPS установите true. При смене порта frontend дополните `APP_ORIGINS`.

Рекомендации для последующего публичного запуска: корпоративный OIDC/SSO для сотрудников, самостоятельное восстановление пароля, аудит изменения доступов и ограничение числа попыток с учётом доверенного reverse proxy. Эти возможности сейчас не выдаются за реализованные.

## Публичный и оценочный API

Порт **8080** — приложение: сессии, UI API и защищённые операции диспетчера. Next.js передаёт cookie и Origin, возвращает Set-Cookie и исходные статусы ошибок.

Контракт организаторов не менялся. Анонимный оценочный API работает на **8081 внутри Docker**, порт не опубликован на компьютере. Он предназначен для доверенного оценочного оркестратора и явных инструментов импорта. Не настраивайте `API_PROXY_TARGET` на него и не публикуйте этот порт рядом с пользовательским приложением. При отдельном запуске оценки организаторам нужно предоставить этот listener в изолированной конфигурации; POST на публичный 8080 теперь требует сессию диспетчера.

| Метод и путь                                    | Назначение                                               |
| ----------------------------------------------- | -------------------------------------------------------- |
| POST /auth/v1/session                           | Вход                                                     |
| GET /auth/v1/session                            | Текущий пользователь                                     |
| DELETE /auth/v1/session                         | Выход                                                    |
| GET /ui/v1/days                                 | Дни для сотрудников                                      |
| GET /ui/v1/days/{date}/workspace                | Полный снимок диспетчера или личная проекция исполнителя |
| GET /ui/v1/days/{date}/staff/{staff}/road-route | Маршрут с проверкой владельца                            |
| POST /ui/v1/days/{date}/events                  | События с проверкой полномочий                           |
| GET, POST /ui/v1/users                          | Управление аккаунтами диспетчером                        |
| PATCH /ui/v1/users/{id}                         | Отключение / восстановление доступа                      |
| GET /ui/v1/requests                             | Все обращения диспетчера или свои у абонента             |
| POST /ui/v1/requests                            | Новое обращение абонента; владельца назначает сервер     |
| PATCH /ui/v1/requests/{id}                      | Ответ и обработка диспетчером                            |

При событиях исполнителя staff_id должен совпадать с аккаунтом, а визит — принадлежать его текущему маршруту. Проверка выполняется под блокировкой дня. Время события задаётся сервером по текущему модельному времени, поэтому исполнитель не может продвинуть часы всей смены. Идентификатор события получает серверное пространство имён пользователя; ответ не раскрывает предупреждения и изменения чужих маршрутов. Правила H1–H10 и существующая дедупликация сохранены.

## Архитектура экранов

Один защищённый App Router layout, общая тема и типизированная конфигурация навигации. Разные задачи получают разные композиции; публичная главная остаётся отдельной страницей.

**Диспетчер:** `/app/dispatch` — операционный центр: сводка смены, фильтруемый список, карта, Гант, риски и журнал. `/app/requests` — отдельная очередь обращений. `/app/admin` — «Центр управления»: обзор ресурсов, карточки СЦ с фактическим числом сотрудников и визитов, поиск по команде, нормативы, доступы, состояние платформы. Навигация сворачивается, имя и полномочия показаны внизу.

**Исполнитель:** `/app/technician` — компактное меню шириной 82 px, без выбора чужих сотрудников. Карта занимает большую часть ширины. Слева — следующий переезд, ближайший визит, оборудование, остановки и сообщение об изменении; ниже — личное расписание. На узком экране карта идёт первой в сетке, затем карточки. MapLibre отслеживает изменение размера контейнера при сворачивании меню.

**Абонент:** `/app/subscriber` — приветствие, заказ услуги, свои обращения и ответы диспетчера. Нет общих карт, модельных часов смены и служебных справочников. Форма содержит услугу, адрес, контакт, пожелание по дате и описание. Список обновляется с сервера.

Черно-фиолетовый градиент и фиолетовые рамки сохранены. Карточки и графики показывают реальные значения, без выдуманных трендов. На рабочих страницах нет тяжёлой hero-анимации. Фокус клавиатуры, названия кнопок и состояний, мобильная навигация и ошибки предусмотрены. Визуальная проверка в браузере не выполнена: оба доступных инструмента не инициализируются.

### Рекомендации для дальнейшего развития дизайна

- Сохранять устойчивое расположение карты и очереди у диспетчера; детали заявки открывать рядом с контекстом, не уводить на новую страницу для каждого действия.
- Для исполнителя держать на первом экране адрес, окно визита, переезд и оборудование. Добавлять реальные статусы выполнения только вместе с соответствующим серверным процессом; текущее положение по расписанию не выдавать за GPS.
- В центре управления отделять наблюдение от изменения данных. Изменение справочников должно предварительно показывать влияние на текущий план, поскольку загрузка reference по контракту сбрасывает дни.
- У абонента использовать простые стадии услуги и согласованные сроки. Технические ПГП, solver и версии плана оставлять внутренним пользователям.
- Развивать общие компоненты: заголовок, панель фильтров, карточка статуса, пустое состояние, форма и боковая панель. Бизнес-проверки сохранять в Go; frontend отвечает за отображение и ввод.

## Обращение и выездной наряд

Обращение проходит NEW → IN_REVIEW → APPROVED либо REJECTED/CLOSED с объяснением. Одобрение сопоставляет адрес со справочником, проверяет норматив и двухчасовой слот, создаёт NEW_ORDER и сохраняет связь с нарядом в транзакции публикации плана. Повторное одобрение возвращает тот же наряд.

Абонент видит назначение или причину ожидания, согласованное окно и подтверждённый исполнителем результат. Исполнитель подтверждает начало и завершение только своих назначенных визитов. Факты выполнения не меняют замороженный план организаторов. Норматив фильтруется по профилю, технологии и типу здания и повторно проверяется сервером.

Повторная отправка обращения с тем же клиентским ключом не создаёт вторую запись; ключ привязан к владельцу. Тело запроса защищено хэшем: изменённые данные с прежним ключом возвращают конфликт.

В «Центре управления» диспетчер может создать пустую смену на новую дату. Используются текущие справочники и матрица; существующие дни не перезаписываются. Затем в диспетчерской строится первоначальный план.

## Запуск и локальные аккаунты

```powershell
cd 'C:\Users\Dmitriy\WebstormProjects\Hakaton(Smart-dispatcher)'
docker compose --profile routing up -d --build --wait
npm run auth:bootstrap
```

Bootstrap создаёт три демонстрационных аккаунта: `dispatcher`, `technician`, `subscriber`. Исполнитель связан с ST-001. У каждого свой случайный пароль. Логины и пароли сохранены в игнорируемом файле **work/demo-accounts.json**. Он предназначен только для локальной демонстрации; не добавляйте его в Git. Существующие аккаунты и их пароли при повторе не изменяются. Для чистой БД сначала загрузите справочники (`npm run demo:load`), затем выполните bootstrap. Обычная сборка не сбрасывает данные.

Вход: http://127.0.0.1:3001/login для текущего локального порта. При ином FRONTEND_PORT используйте его. Новые аккаунты создаются диспетчером в «Центр управления → Доступы»; публичная регистрация не реализована.

Для разработки frontend: `npm run dev` после запуска Go; защищённые рабочие экраны всегда используют серверные данные. Старые mock-компоненты оставлены в исходниках, но не подключены к рабочим маршрутам.

Проверки: `docker compose --profile test run --build --rm tests`, `npm run typecheck`, `npm run lint`, `npm run test` и production-сборка Docker. Есть тесты изоляции ролей, чужого маршрута и обращения, запрета чужих событий, истечения и отзыва сессии, блокировки пользователя, Origin, лимита входа и прохождения cookie через proxy. Старые тесты планирования и событий сохранены.
