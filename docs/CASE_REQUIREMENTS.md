# Сверка требований и учебных данных

Переданное краткое ТЗ соответствует основному направлению проекта: 40 сотрудников, 5 СЦ, 350–450 нарядов, две смены, допуски, оборудование и событийное перепланирование. Его учитываем как описание задачи; точные поля и правила проверяем по `contracts/api_spec.yaml`.

## Что означает число сотрудников

Ранее интерфейс показывал двух сотрудников из минимальных примеров OpenAPI. Это размер загруженного справочника, а не лимит программы. Существовавшие нагрузочные тесты 40/400 использовали упрощённые копии сотрудников и одного адреса; они не заменяют полноценный разнотипный учебный набор.

Теперь в `data/synthetic` подготовлен отдельный набор: 28 ЛТП + 12 инсталляторов, 5 СЦ, 50 узлов и 100 учебных адресов, 400 нарядов, направленная дорожная матрица и пример событий. Файлы имеют имена организаторов. Набор проходит тот же валидируемый API, что и будущие внешние данные. При получении официальных файлов их можно импортировать без переписывания интерфейса.

## Точные ограничения

| Правило                         | Реализация/уточнение                                                                                                                            |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| H1: профиль, технология, высота | Все три допуска проверяются независимо; неподходящий сотрудник не получает визит                                                                |
| H2: смена                       | Все остановки и возвращение укладываются в назначенную смену                                                                                    |
| H3: обед                        | При наличии визитов ровно один BREAK, не короче нормы; начало в break_window, без пересечения остановок                                         |
| H4: окно                        | Начало между slot.start и latest_start. latest_start вычисляется из max_start_delay_min конкретного типа работ; для учебных INST_* это 10 минут |
| H5: норматив                    | Длительность визита из work_types.csv; изменение только разрешёнными событиями                                                                  |
| H6: дорога                      | Ограничения расписания проверяются по единой направленной матрице, а не прямым линиям или внешним пробкам                                       |
| H7: оборудование                | Списание при начале визита, запас неотрицателен; RESTOCK пополняет до capacity                                                                  |
| H8: СЦ                          | Начало/конец в СЦ сотрудника; пополнение возможно в любом открытом СЦ с соблюдением длительности                                                |
| H9: полнота                     | Каждый наряд ровно в одном месте: визит, Unassigned, ПГП или Cancelled                                                                          |
| H10: история                    | Уже начатые остановки сохраняются; изменения выполняются по правилам событий                                                                    |

«Штраф за нарушение» в оценке не означает, что наш алгоритм должен сознательно нарушать жёсткие ограничения. Кандидат отклоняется независимым валидатором, а неподходящий наряд остаётся явно нераспределённым с причиной.

Краткое ТЗ перечисляет три вида событий. Полный контракт содержит шесть: NEW_ORDER, ORDER_CANCELLED, VISIT_DELAYED, ORDER_TRANSFERRED, STAFF_UNAVAILABLE и TIME_TICK. Все шесть уже реализованы. ПГП, ранние предупреждения о рисках, повторные обращения с весом и сроки ответа также остаются в объёме кейса.

Нормативы и распределение нашего набора демонстрационные; это не заявление об исходных данных Ростелекома. Сгенерированные данные предназначены для разработки и воспроизводимой демонстрации. Качество алгоритма необходимо дополнительно проверять на других seed/днях и независимых сценариях.

AI-помощник исключён решением команды. PyVRP интегрирован в первоначальный план: предложения восстанавливаются и проверяются Go. На учебном наборе измерен выигрыш над baseline; события остаются в Go. Полная модель ограничений не делегируется бесплатному решателю. Метрики и ограничения описаны в [PYVRP.md](PYVRP.md).
