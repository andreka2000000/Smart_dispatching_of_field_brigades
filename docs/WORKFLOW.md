# Сквозной процесс МаксТелеком — версия 0.9.0

Реализовано 14 ноября 2026 года. Обращение абонента теперь связано с выездным нарядом и подтверждением исполнителя. Защищённые страницы работают с Go/PostgreSQL через Next.js proxy.

Короткий сценарий без API/SQL: [DEMO_CHECKLIST.md](DEMO_CHECKLIST.md). В «Центре управления» доступна «Новая смена»; она не перезаписывает существующие дни. Повторная отправка обращения защищена клиентским ключом и уникальным индексом на владельца/ключ.

## Как провести демонстрацию

1. Войти как subscriber. Открыть «Мои обращения», нажать «Заказать услугу» и отправить обращение. Если хотите использовать существующие учебные смены, укажите 29 октября 2026 года; система работает с модельной датой, а не с календарём компьютера.
2. В отдельном браузерном профиле войти как dispatcher. В «Обращения абонентов» выбрать нужную смену в заголовке. У неё должен быть первоначальный план.
3. Нажать «Одобрить и распределить». Сопоставить адрес абонента с адресом и технологией из справочника, выбрать норматив, двухчасовой слот и оборудование. Для PON/FTTB и типа здания список нормативов фильтруется, выбор также проверяется сервером. Подтвердить, что окно согласовано с абонентом.
4. Сервер выдаст свободный номер ORD-YYYYMMDD-NNNN, зарегистрирует NEW_ORDER, пересчитает план и сохранит связь с обращением в одной транзакции. Повторное нажатие не создаёт второй наряд. Ошибка сохранения откатывает план, событие и связь.
5. В карточке диспетчера появятся сотрудник и его staff_id. При отсутствии назначения будет показана причина ожидания. Одобрение не гарантирует наличие свободного подходящего исполнителя.
6. Исполнителем может стать любой подходящий сотрудник. Аккаунт technician связан только с ST-001. Для другого сотрудника создайте аккаунт через «Центр управления → Доступы», указав соответствующий staff_id.
7. При необходимости продвиньте модельное время: «Диспетчерская → Добавить событие → Обновление времени». Укажите время начала назначенного визита или немного позже. Время всего дня меняет диспетчер, не исполнитель.
8. Войти под аккаунтом назначенного исполнителя. В разделе «Фактическое выполнение → Мои задания» нажать «Начать работу», затем заполнить результат и нажать «Подтвердить выполнение».
9. Абонент увидит назначение, согласованное окно, начало работы и итоговый отчёт. В списке диспетчера статус также обновится. Данные перечитываются автоматически, исполнитель обновляет свой снимок сразу после подтверждения.

Вкладки одного браузерного профиля разделяют сессию: для параллельной проверки ролей используйте разные профили или обычное окно и инкогнито.

## Состояния

Обращение: NEW → IN_REVIEW → APPROVED. Вместо одобрения можно отклонить с объяснением (REJECTED) либо решить вопрос без выезда (CLOSED). Одобренное обращение нельзя произвольно закрыть старой кнопкой, обходя жизненный цикл наряда.

Связанный наряд: SCHEDULED, UNASSIGNED, IN_PROGRESS, COMPLETED. Отмена через событие диспетчера даёт CANCELLED, ПГП — STATION. Если учебный день заменён импортом, старое обращение получает REQUIRES_REVIEW; оно не связывается с новым нарядом по совпадению номера.

Результат «Выполнена» теперь требует подтверждения исполнителя. После планового окончания без подтверждения показывается «Ожидает подтверждения». Плановое наступление визита отмечается как «Окно визита идёт», отдельно от фактического начала.

## Границы и хранение

- request_orders связывает обращение, день, поколение, наряд и результат события. Запись создаётся в транзакции публикации плана. Проверяются текущий статус обращения и актуальность снимка.
- visit_facts хранит исполнителя, модельное время начала/завершения и отчёт. Повтор START/COMPLETE не дублирует факт и не переводит завершённую работу назад.
- Факты выполнения не переписывают замороженное расписание оценочного API. Автоматическое сокращение поездки или освобождение времени после раннего завершения не заявляется реализованным.
- Исполнитель подтверждает только визиты своего текущего маршрута. До начала визита по модельному времени действие запрещено. Абонент получает только сведения связанного со своим обращением наряда.
- Контрольный срок вычисляется сервером из норматива: HOURS от регистрации, SLOT по окну, WORKING_DAYS с исключением субботы и воскресенья. Производственный календарь праздничных дней организаторами не предоставлен и не моделируется.
- Адрес сопоставляет диспетчер. Геокодирование произвольного адреса и автоматическое создание нового здания пока отсутствуют.
- Новое обращение распределяется событийным Go-планировщиком. PyVRP остаётся в первоначальном планировании.

## Проверка

Пройдены интеграционные тесты PostgreSQL: обращение → одобрение → назначение → старт → завершение → отчёт абоненту; запрет чужих действий; повторное одобрение; отказ; полный rollback при искусственной ошибке связи. Все прежние тесты планирования, событий и H1–H10 сохранены.

Дополнительно весь сценарий проверен реальными HTTP-запросами через production Next.js proxy на отдельном временном учебном дне. Диспетчер получил назначение ST-021, для него был создан временный аккаунт, абонент увидел COMPLETED и отчёт. Временные аккаунт, обращение и день удалены, исходные смены 28/29 октября сохранены. Локальный результат: work/workflow-validation.json.

Frontend: 20 тестов, включая рендер карточек всех состояний и защиту панели управления от отсутствующего списка отсутствующих сотрудников. TypeScript, lint и production-сборка пройдены. Визуальная приёмка в браузере остаётся непроверенной из-за недоступности инструментов управления браузером.

## Остаток до защиты

Независимые наборы и повторные замеры производительности; визуальная приёмка всех страниц и мобильных размеров; финальная репетиция без ручного вмешательства в БД. Для массового изменения справочников нужен отдельный безопасный процесс с предварительным просмотром влияния на план. Текущие таблицы справочников предоставляют просмотр, а не редактор.
